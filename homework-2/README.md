## 2. Данные и запросы

**Валидатор.** Поставил на коллекцию `products` через `collMod` с `$jsonSchema`: `_id`/`name`/`category` — строки, `price` — decimal (минимум 0), `variants` — массив из `{size: строка, stock: целое, минимум 0}`. Режим `validationLevel: strict`, `validationAction: error`

**Поиск.** Фильтрую по категории и вариантам через `$elemMatch`, чтобы размер и достаточный остаток были из одного варианта:

```js
db.products.find({ category, variants: { $elemMatch: { size, stock: { $gte: qty } } } }).sort({ _id: 1 })
```

Контрпример из задания сошелся: у A размер L имел остаток 0 (M — 10), поэтому две единицы L его не возвращали, а после изменения A/L на 2 — вернулся. Остальные входы тоже совпали (clothes/L/2 → B,C; clothes/M/5 → A; accessories/L/3 → D; clothes/L/99 → [])

**История.** `historyCursor` — фильтр по `userId` и `status`, сортировка `createdAt: -1, _id: 1`, лимит 20. Тот же курсор переиспользуется в опыте с индексом. Контрольная история (`userId: 2500, status: paid`) вернула 20 документов в нужном порядке, при равных датах — по возрастанию `_id`. С другим покупателем, статусом и без совпадений — тоже корректно

**Почему такая модель.** Позиции встроены в заказ, потому что заказ и его состав читаются и пишутся вместе — так весь заказ достается одним чтением, без join-ов, а сами позиции без заказа бессмысленны. История покупателя — это отдельные документы заказов, а не массив внутри пользователя, иначе документ пользователя рос бы без конца и историю пришлось бы читать и сортировать целиком. Отдельные заказы можно резать лимитом и индексировать по `userId`. Цена в позиции — это цена на момент покупки, снимок на тот момент. Каталог хранит текущую цену («сколько стоит сейчас»), а позиция — фактическую («сколько заплатили тогда»), чтобы выручка не пересчитывалась при смене цены

## 3. Отчет о продажах

Конвейер: `$match` по `status: paid` и периоду `[from, to)`, `$unwind` по позициям, `$group` по sku (`qty = $sum(qty)`, `revenue = $sum($multiply[qty, price])`), `$lookup` названия из products, `$sort` по убыванию выручки, потом по артикулу, `$limit 5`. `revenue` считается прямо в pipeline, поэтому остается Decimal128

Расчет товара A по позициям: в `sale-start` A/M/2 по 100.00 → 2×100.00 = 200.00, в `sale-middle` A/L/1 по 120.00 → 1×120.00 = 120.00. Итого qty = 3, revenue = 320.00. После смены цены A в каталоге на 999.00 отчет не поменялся — выручка берется из позиции, а не из текущей цены

## 4. Индекс и план выполнения

Запрос истории `{userId: 2500, status: paid}` на 10 000 заказов. Составной индекс:

```js
{ userId: 1, status: 1, createdAt: -1, _id: 1 }
```

Порядок полей по правилу ESR: сначала equality по `userId` и `status`, потом sort по `createdAt` и `_id`. Равенства сужают диапазон, сортировочные поля дают результат уже в нужном порядке без отдельного SORT. `hint` не применял, MongoDB сама выбрала индекс

| Вариант | nReturned | totalKeysExamined | totalDocsExamined | Есть отдельная SORT |
|---|---:|---:|---:|---|
| До индекса | 20 | 0 | 10000 | да |
| После индекса | 20 | 20 | 20 | нет |

До индекса — `COLLSCAN` (все 10 000 документов) + отдельный `SORT`. После — `IXSCAN` по составному индексу: проверено и прочитано ровно 20 документов, SORT нет. Список `_id` и его порядок до и после совпали (лежат в `results.json` как `beforeIds`/`afterIds`)

Издержка индекса: теперь при вставке/обновлении/удалении заказа WiredTiger обновляет и `_id_`, и новый индекс — это лишние записи на диск и в память (замедление записи, рост места) в обмен на быстрый путь чтения по `userId`+`status`

## 5. Оформление заказа (транзакция)

Покупка выполняется в одной многодокументной транзакции и одной сессии (обертка `transaction()` из `lab.js`). Параметры — `readConcern: snapshot`, `writeConcern: {w: majority, j: true}`, `readPreference: primary`

Сначала проверяю заказ по `operationId`: если он уже есть и совпадает с запросом — возвращаю его (повтор, ничего не пишу), если есть, но параметры другие — `REQUEST_CONFLICT`. Дальше по каждой позиции нахожу товар (для цены на момент покупки) и делаю `updateOne` со списанием `$inc {'variants.$.stock': -qty}` и условием на остаток прямо в фильтре (`$elemMatch {size, stock: {$gte: qty}}`). Если `matchedCount === 0` (нет размера/SKU или не хватает остатка) — `ITEM_UNAVAILABLE`. Результат первого успешного обновления отдаю в `trace`. В конце вставляю заказ `{_id, userId, createdAt, status: "created", items}`. Все операции — через базу в активной сессии; если внутри брошено исключение, обертка делает `abortTransaction`, иначе `commitTransaction`

Атомарность и защита от повтора — это разные вещи. Атомарность дает транзакция: списание двух остатков и вставка заказа «все или ничего», если второй товар недоступен, первое списание откатывается. А защита от повтора (идемпотентность) — отдельная проблема: транзакция не знает, что запрос уже выполнялся (например, после commit потерялся ответ). За это отвечает проверка по `operationId` — повтор с теми же параметрами возвращает сохраненный заказ, конфликт отклоняется. То есть транзакция дает атомарность одного выполнения, а идемпотентность — это бизнес-логика поверх

## 6. Смена primary (failover)

Клиент находит новый primary так: он подключен по seed-списку (`mongodb://m1:27017,m2:27017,m3:27017?replicaSet=hw2rs`), следит за топологией через `hello`, и когда `stepDown` переводит m1 в secondary, а m2 выигрывает выборы, монитор видит нового primary и направляет записи на него. Адрес подключения менять не нужно

`writeConcern: majority` значит, что запись зафиксирована на большинстве узлов, но не что каждый secondary уже ее применил — репликация асинхронная, secondary может отставать по oplog, и чтение с нее вернет старые данные. Чтобы читать зафиксированное большинством, нужен `readConcern: majority` (или причинная согласованность через `afterClusterTime`). В опыте я читал с primary, поэтому сразу видел актуальные данные

## 7. Шардирование

`orders` шардирована по `{userId: 1}`: меньше 2000 → A, 2000–5000 (не включая) → B, от 5000 → A

История `{userId: 2500}` содержит равенство по полному ключу шардирования, поэтому `mongos` по диапазону определяет шард B и опрашивает только его. Один участник

Отчет `{status: "paid"}` — в фильтре нет ключа шардирования, `mongos` не может понять, где лежат документы, и делает broadcast на оба шарда (A и B), а потом объединяет

Индекс `{status: 1}` внутри шардов число участников не изменит: маршрутизация зависит только от ключа шардирования, которого в фильтре нет. Но внутри каждого шарда вместо collection scan по `status` теперь используется этот индекс — шард быстрее находит paid-заказы и читает меньше документов. То есть индекс снижает работу каждого участника, но не сокращает список участников
